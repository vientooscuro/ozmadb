# OzmaDB: анализ производительности F#-кода

Дата: 2026-08-25. Ревизия: `f6fe3b2`. Объём анализа: ~53k строк рукописного F# (`OzmaDB/src`, `OzmaUtils/src`).

## Статус: реализовано и измерено

Работа выполнена в ветке `worktree-perf-optimizations`. Ниже — результаты, полученные на изолированном стенде: два контейнера (`ozmadb-perf` с правками и `ozmadb-base` на `f6fe3b2`), каждый со своим PostgreSQL, одинаковая схема, 2000 строк данных, две роли с непересекающимися фильтрами.

### Итоговое A/B (медиана / p90, мс)

Методика: оба контейнера перезапущены, одинаковый прогрев (1200 запросов на сторону, чтобы tiered JIT вышел на tier1), затем 200 замеров с рандомизацией порядка сторон.

| Сценарий | perf | base | медиана | p90 |
|---|---|---|---|---|
| роль, limit 1 | 3.15 / 3.88 | 3.80 / 4.41 | **+17.2 %** | +12.1 % |
| роль, limit 50 | 3.92 / 4.85 | 4.63 / 5.52 | **+15.3 %** | +12.2 % |
| роль, 600 строк | 8.93 / 10.02 | 9.90 / 10.94 | **+9.8 %** | +8.4 % |
| root, limit 1 | 3.26 / 3.99 | 3.83 / 4.59 | **+15.0 %** | +13.0 % |
| root, 2000 строк | 20.97 / 23.90 | 22.27 / 25.01 | **+5.8 %** | +4.4 % |

**Тела ответов побайтово идентичны во всех сценариях** — это основная проверка того, что оптимизации ничего не изменили в семантике.

Выигрыш больше на лёгких запросах и меньше на тяжёлых: оптимизирована фиксированная часть запроса, а на выборке в 2000 строк начинает доминировать передача данных и работа PostgreSQL.

Отдельно: стенд держит БД в соседнем контейнере, то есть RTT около 0.1 мс. Правка с TTL на проверку версии убирает три round-trip, поэтому **в продакшене с сетевой БД её вклад будет заметно больше, чем видно здесь**.

### Вклад кэша прав, измеренный отдельно

Самая рискованная правка проверялась изолированно: тот же бинарь, та же БД, отличается только обращение к кэшу.

| Сценарий | с кэшем | без кэша | выигрыш |
|---|---|---|---|
| роль, limit 1 | 6.03 | 10.47 | **+42.4 %** |
| роль, limit 50 | 6.83 | 10.39 | **+34.2 %** |
| роль, 600 строк | 13.73 | 14.59 | +5.9 % |

То есть `applyPermissions` + `applyRoleViewExpr` занимали около **4.4 мс на каждый запрос** — и это на схеме из одной пользовательской сущности с одним правилом. На реальной схеме с сотнями сущностей эта величина только растёт.

### Проверки корректности

- **Изоляция ролей.** Три раунда чередования `root` → `reader_low` → `reader_high` при прогретом кэше: количество строк и состав данных совпадают с baseline в каждом случае, пересечения между ролями нет.
- **Инвалидация.** Изменение условия роли (`bucket < 5` → `bucket < 3`) немедленно отражается в результатах: 1000 строк → 600 строк, идентично baseline.
- **Миграция.** Обе БД инициализированы с нуля правленым бинарём, схема создана, пользовательская схема с сущностью и полями заведена через API.

### Замечание о методике измерений

Первые два прогона дали противоречивые результаты (сначала +21 %, потом −24 % на тех же сценариях). Причина — неравные условия: контейнер с правками был только что перезапущен, а baseline работал час и был полностью прогрет. Под .NET с tiered compilation прогрев в 12–30 запросов недостаточен. Итоговые цифры выше получены только после того, как обе стороны были приведены в одинаковое состояние. **Если будете перепроверять — перезапускайте оба инстанса и прогревайте одинаково, иначе результат не значит ничего.**

## Важная оговорка о методе

В репозитории нет ни бенчмарков, ни профилей, ни нагрузочных тестов, поэтому всё ниже – **статический анализ горячих путей**, а не измерения. Находки отранжированы по ожидаемому эффекту и уверенности, но порядок величин – оценки. Раздел «Как измерять» в конце описывает, чем эти гипотезы подтвердить до того, как что-то переписывать.

Ключевой вывод: узкие места сосредоточены не в «языке», а в трёх местах – **фиксированные накладные расходы на каждый запрос**, **работа на каждую строку результата** и **сериализация ответа через рефлексию**. Ни одно из них не требует смены языка.

## Карта горячего пути

Один вызов `GET /views/.../entries` проходит:

1. `ContextCacheStore.GetCache` → `getCachedState` – **открытие соединения + транзакция + запрос версии состояния + rollback** ([ContextCache.fs:915](../OzmaDB/src/API/ContextCache.fs#L915))
2. `DatabaseTransaction.Begin` – **вторая** транзакция, уже рабочая
3. `resolveSource` – поиск user view в кэше (для named – готовый, для anonymous – компиляция)
4. `applyPermissions` + `applyRoleViewExpr` – **пересборка всего AST под роль** ([UserViews.fs:258](../OzmaDB/src/API/UserViews.fs#L258))
5. `resolveViewExprChunk` + `queryExprChunk` – ещё одна модификация AST
6. `viewExpr.Query.Expression.ToSQLString()` – **рендеринг AST в строку** ([Query.fs:790](../OzmaDB/src/OzmaQL/Query.fs#L790))
7. Выполнение в PG + `parseType` на каждую колонку ([SQL/Query.fs:317](../OzmaDB/src/SQL/Query.fs#L317))
8. `parseRow` на каждую строку ([Query.fs:589](../OzmaDB/src/OzmaQL/Query.fs#L589))
9. Сериализация Newtonsoft через рефлексию ([HTTP/Utils.fs:230](../OzmaDB/src/HTTP/Utils.fs#L230))

Шаги 4–6 не кэшируются вообще; шаг 1 – чистые накладные расходы; шаги 7–9 линейны по объёму данных с большой константой.

## P0. Лишние round-trip к PostgreSQL на каждый запрос

**Где:** [ContextCache.fs:404-410, 915-971](../OzmaDB/src/API/ContextCache.fs#L404), [Connection.fs:201](../OzmaDB/src/Connection.fs#L201)

Каждый HTTP-запрос перед началом полезной работы делает:

```
BEGIN                                     -- RTT 1
SELECT ... FROM state WHERE name='StateVersion' LIMIT 1   -- RTT 2
ROLLBACK (dispose)                        -- RTT 3
BEGIN                                     -- RTT 4, уже рабочая транзакция
```

`getCachedState` открывает отдельную транзакцию **исключительно** ради чтения одной строки версии схемы, закрывает её и открывает новую. Комментарий в `GetCache` прямо говорит, что это сделано «to minimize locking» и что гонки с миграцией допустимы.

**Эффект.** Три лишних round-trip. При RTT 0.3 мс (сокет на том же хосте) – примерно +1 мс; при RTT 5 мс (БД в другой зоне) – примерно +15 мс на каждый запрос, независимо от его сложности. Для запросов, которые сами выполняются 5–20 мс, это от 10 до 50 % общей латентности. Это, скорее всего, самая крупная и самая дешёвая в исправлении находка.

**Что делать (по возрастанию сложности):**

1. **Кэш версии с коротким TTL.** Проверять `StateVersion` не чаще раза в N мс (100–500 мс достаточно: миграции редки, а «рассинхронизация на полсекунды» уже допущена архитектурно). Одна строка кода в `getCachedState`, эффект – минус 3 RTT почти со всех запросов.
2. **Совместить с рабочей транзакцией.** Читать версию в той же транзакции, где выполняется запрос, вместо отдельной. Убирает RTT 1 и 3.
3. **`LISTEN`/`NOTIFY`.** Мигратор шлёт `NOTIFY ozmadb_state`, инстансы держат подписку и инвалидируют кэш событийно. Убирает опрос полностью и заодно чинит гонку, а не маскирует её. Самый правильный вариант, но требует выделенного соединения на инстанс.

Начать стоит с (1) – это правка на десяток строк, которую можно измерить за день.

## P0. Права и chunk пересчитываются на каждый запрос

**Где:** [UserViews.fs:255-295](../OzmaDB/src/API/UserViews.fs#L255), [Permissions/Apply.fs:604-634](../OzmaDB/src/Permissions/Apply.fs#L604)

Для любого запроса от неройтовой роли выполняется:

```fsharp
let appliedDb = applyPermissions ctx.Layout role uv.UserView.Compiled.UsedDatabase
applyRoleViewExpr ctx.Layout appliedDb uv.UserView.Compiled
```

`applyPermissions` строит и сливает F#-мапы по всему дереву использованных сущностей (`Map.toSeq |> Seq.map |> Seq.fold Map.unionUnique`), `applyRoleViewExpr` затем **перестраивает весь скомпилированный AST**, вставляя RLS-фильтры. Дальше `resolveViewExprChunk` и `queryExprChunk` перестраивают его ещё раз под limit/offset/where.

Всё это – чистая функция от `(view, role, chunk-shape)`. Роли меняются редко, набор view фиксирован, форма chunk у клиента обычно одна и та же (меняются только значения limit/offset, а они уходят в параметры). При этом результат не кэшируется ни на секунду.

**Эффект.** Для крупного layout это десятки-сотни тысяч операций над персистентными деревьями и полная пересборка AST – ориентировочно единицы-десятки миллисекунд CPU на запрос, целиком на горячем пути и целиком повторяемая.

**Что делать.** Кэш `(userViewRef | anonymousQueryHash, roleRef, chunkShape) → CompiledViewExpr`, инвалидируемый вместе с `cachedState` (там уже есть `clearCaches()`). Ключ по `chunkShape`, а не по значениям – limit/offset должны быть плейсхолдерами, а не константами в AST, иначе кэш не попадёт и заодно испортится Npgsql auto-prepare (см. P2).

Это самая большая по объёму работа из списка, но и самый большой выигрыш по CPU.

## P1. Рендеринг SQL: `sprintf` по дереву AST

**Где:** [SQL/AST.fs](../OzmaDB/src/SQL/AST.fs) (92 вызова `sprintf`), [OzmaQL/AST.fs](../OzmaDB/src/OzmaQL/AST.fs) (96), [SQL/DDL.fs](../OzmaDB/src/SQL/DDL.fs) (57). Всего по проекту 556 вызовов семейства `sprintf`.

Каждый узел AST рендерит себя в **новую строку**, родитель конкатенирует детей:

```fsharp
| VEAnd(a, b) -> sprintf "(%s) AND (%s)" (a.ToSQLString()) (b.ToSQLString())
| VEFunc(name, args) -> sprintf "%s(%s)" (name.ToSQLString()) (args |> Seq.map toSQLString |> String.concat ", ")
```

Две отдельные проблемы:

**Квадратичность.** Для дерева из n узлов глубины d символы копируются O(n·d) раз. Запрос user view после вставки RLS – это легко несколько тысяч узлов, то есть сотни килобайт лишних копирований и тысячи промежуточных строк в Gen0 на каждый запрос.

**Стоимость самого `sprintf`.** В F# `sprintf` – не форматирование строки, а построение и интерпретация `PrintfFormat` со специализацией по типам. Даже с ускорениями в FSharp.Core 6+ он остаётся на порядок дороже интерполяции и на два порядка дороже `StringBuilder.Append`. В `ToSQLString` он вызывается на каждый узел.

**Что делать.** Перевести `ToSQLString` на `StringBuilder`, передаваемый по дереву:

```fsharp
type ISQLString =
    abstract member WriteSQL: StringBuilder -> unit

// ToSQLString остаётся тонкой обёрткой для совместимости:
let toSQLString (x: #ISQLString) =
    let sb = StringBuilder()
    x.WriteSQL sb
    sb.ToString()
```

Один буфер на запрос вместо тысяч строк, ноль `sprintf` на горячем пути. Правка механическая и локальная (два файла, ~190 мест), покрывается тестами «запрос → ожидаемый SQL», которых сейчас нет и которые в любом случае нужны.

Отдельно: `sprintf` в путях ошибок (`raisef`, `failwithf`) трогать не надо – они холодные.

## P1. Парсер SQL-типов на каждую колонку каждого запроса

**Где:** [SQL/Query.fs:48, 264, 317](../OzmaDB/src/SQL/Query.fs#L48)

```fsharp
let private parseType typeStr =
    match parse tokenizeSQL valueType typeStr with   // FsLexYacc: лексер + LALR-парсер
    ...

let getColumn i =
    let typ = parseType (reader.GetDataTypeName(i))   // на каждую колонку
```

На каждый результат запроса для каждой колонки запускается полноценный сгенерённый лексер и парсер, чтобы разобрать строку вида `integer` или `character varying(255)`. Множество различных имён типов в PostgreSQL – конечное и маленькое (десятки).

**Эффект.** Запрос с 30 колонками – 30 запусков FsLexYacc-парсера, каждый с аллокацией буферов лексера. Это порядка десятков микросекунд на колонку, то есть до миллисекунды на запрос, целиком выбрасываемой впустую.

**Что делать.** Мемоизация:

```fsharp
let private typeCache = ConcurrentDictionary<string, SimpleValueType>()
let private parseType (typeStr: string) =
    typeCache.GetOrAdd(typeStr, parseTypeUncached)
```

Три строки, риск нулевой (функция чистая), эффект измеримый. Самая выгодная правка на единицу усилий во всём списке.

Дополнительно: в `ExecuteRowValuesQuery` ([SQL/Query.fs:264](../OzmaDB/src/SQL/Query.fs#L264)) `parseType` вызывается внутри `getValue`, то есть заново для каждой считываемой строки, а не один раз на колонку, как в `ExecuteQuery`. Стоит выровнять с `ExecuteQuery` – вынести разбор колонок из построчного цикла.

## P1. `parseRow`: построение деревьев на каждую строку результата

**Где:** [OzmaQL/Query.fs:589-680](../OzmaDB/src/OzmaQL/Query.fs#L589)

Функция вызывается **для каждой строки** результата. Что она делает на каждой строке:

```fsharp
let attrs = Map.map (fun name (valType, i) -> values.[i]) cellAttributes   // новый Map на ячейку
match Map.tryFind column.Name punAttributes with ...                      // поиск по строковому ключу на ячейку
let domainIds = Map.mapMaybe (fun ns i -> getDomainId i) domainColumns     // новый Map на строку
let getEntityIds fields = fields |> Map.values |> Seq.mapMaybe getEntityId |> Map.ofSeq  // ещё один Map
let rowAttrs = Map.map (fun name (valType, i) -> values.[i]) rowAttributes // ещё один Map
let mid = idColumns |> Map.find info.IdColumn |> getId                    // поиск по строковому ключу
```

Проблема концептуальная: **вся раскладка колонок известна и неизменна на весь запрос**, но в цикле по строкам она заново разбирается через ассоциативные структуры со строковыми ключами и заново материализуется в персистентные деревья.

Особенно показателен `Map.tryFind column.Name punAttributes` внутри `getCell`: индекс pun-колонки уже вычислен на этапе построения `columnsMeta` строкой выше – и всё равно ищется заново для каждой ячейки каждой строки.

**Эффект.** На результате 5 000 строк × 30 колонок: 150 000 поисков по строковым ключам в красно-чёрных деревьях плюс порядка 20 000 построений новых `Map`, каждое с аллокацией узлов. Это доминирующая стоимость обработки больших выборок, легко десятки миллисекунд и мегабайты мусора.

**Что делать.** Предвычислить на запрос плоские массивы индексов и в цикле работать только по `int`:

```fsharp
// один раз на запрос
type CellPlan = { ValueIdx: int; PunIdx: int voption; AttrIdxs: (OzmaQLName * int)[] }
let cellPlans: CellPlan[] = ...

// в цикле по строкам – только индексация
let getCell (plan: CellPlan) =
    { Value = values.[plan.ValueIdx]
      Pun = match plan.PunIdx with ValueSome i -> Some values.[i] | ValueNone -> None
      Attributes = ... }
```

Там, где на выходе всё-таки нужен `Map` (это часть публичного контракта `ExecutedRow`), строить его из отсортированного массива, а пустой – переиспользовать `Map.empty`, а не создавать через `Map.map` над пустым источником.

## P1. Сериализация ответа: рефлексия на каждое поле каждого объекта

**Где:** [OzmaUtils/Serialization/Json.fs:370-384](../OzmaUtils/src/Serialization/Json.fs#L370), [OzmaUtils/Reflection.fs:76-80](../OzmaUtils/src/Reflection.fs#L76)

В `ConverterContractResolver.CreateProperty`:

```fsharp
prop.ShouldSerialize <-
    fun obj ->
        let value = fieldInfo.GetValue(obj)
        value <> prop.DefaultValue
```

а `GetValue` – это:

```fsharp
let getMemberValue (memberInfo: MemberInfo) =
    match memberInfo with
    | :? PropertyInfo as info -> Some info.GetValue    // рефлексия
    | :? FieldInfo as info -> Some info.GetValue
```

Три проблемы в одном месте:

1. **`PropertyInfo.GetValue` – рефлексивный вызов** (~100–200 нс против ~2 нс у скомпилированного делегата). Вызывается для каждого поля каждого сериализуемого объекта.
2. **Значение читается дважды:** один раз в `ShouldSerialize`, второй – самим Newtonsoft через `ValueProvider`.
3. **`value <> prop.DefaultValue` – это F#-generic equality на `obj`.** Для боксированных значений это уход в `GenericEqualityIntrinsic` с проверками интерфейсов и, для структурных типов, рекурсивным сравнением. Дорого и неочевидно.

**Эффект.** Ответ user view – это `ExecutedRow[]`, где каждая строка содержит `ExecutedValue[]`, а каждый `ExecutedValue` – запись из трёх полей ([OzmaQL/Query.fs:87](../OzmaDB/src/OzmaQL/Query.fs#L87)). На 5 000 строк × 30 колонок это 150 000 записей × 3 поля = **450 000 рефлексивных вызовов только в `ShouldSerialize`**, плюс столько же generic-сравнений, плюс столько же чтений в самом сериализаторе. Порядок – сотни миллисекунд CPU на крупный ответ.

**Что делать:**

1. Заменить `info.GetValue` на скомпилированный делегат через `Expression.Lambda<Func<obj,obj>>` или `Delegate.CreateDelegate` (кэшируется в `SerializableField`, строится один раз на тип). Эффект – порядок величины на этой операции.
2. Заменить `value <> prop.DefaultValue` на нежадное сравнение: сначала ссылочное `obj.ReferenceEquals`, затем типизированное `Object.Equals`. Generic equality здесь не нужна.
3. Устранить двойное чтение: выставлять `prop.ValueProvider` тем же делегатом, что использует `ShouldSerialize`.

Отдельно, дешёвая правка рядом: [Json.fs:122](../OzmaUtils/src/Serialization/Json.fs#L122) – `objInfo.Cases.[tag]` ищет случай DU в `Map<int, _>` (дерево) вместо индексации массива. Для `Value` с 27 случаями это ~5 сравнений на каждое сериализуемое значение вместо одной индексации. Замена `Map<int,_>` на массив по тегу – механическая.

Хорошая новость: `Value` и `FieldValue` уже имеют быстрые ручные конвертеры (`ValuePrettyConverter`, [SQL/AST.fs:191](../OzmaDB/src/SQL/AST.fs#L191)), так что сами значения ячеек сериализуются нормально. Дорогá – обёртка вокруг них.

## P2. Кэш анонимных view: 64 элемента и `DateTime.Now`

**Где:** [ContextCache.fs:155-175](../OzmaDB/src/API/ContextCache.fs#L155)

```fsharp
// FIXME: random values.
let anonymousViewsCache =
    FluidCache<AnonymousUserView>(64, TimeSpan.FromSeconds(0.0), TimeSpan.FromSeconds(600.0), fun () -> DateTime.Now)
```

Комментарий не врёт – значения выбраны наугад. Два замечания:

- **64 элемента** на все анонимные user views инстанса. Любой клиент, который шлёт больше 64 различных ad-hoc запросов (типичный сценарий для UI с динамическими выборками), получает постоянное вытеснение и **полную перекомпиляцию OzmaQL → SQL** на промахе. Это худший из возможных промахов кэша в системе.
- **`DateTime.Now` вместо `DateTime.UtcNow`.** `Now` конвертирует в локальную таймзону, что заметно дороже; вызывается при каждом обращении к кэшу. При `InvariantGlobalization=true` это ещё и бессмысленно.

**Что делать.** Поднять ёмкость (512–4096, память на скомпилированный view невелика относительно эффекта), заменить `DateTime.Now` на `DateTime.UtcNow`, и вынести обе величины в конфиг, чтобы их можно было крутить без пересборки. Заодно – метрика hit/miss (Prometheus уже подключён), без неё подбор размера остаётся угадыванием.

## P2. Комментарий в тексте SQL ломает auto-prepare

**Где:** [OzmaQL/Query.fs:719, 790](../OzmaDB/src/OzmaQL/Query.fs#L719), [API/UserViews.fs:29-46](../OzmaDB/src/API/UserViews.fs#L29)

`Max Auto Prepare = 50` выставлен ([Program.fs:223](../OzmaDB/src/Program.fs#L223)) – Npgsql кэширует подготовленные выражения по **тексту** запроса. Но перед каждым запросом подставляется префикс-комментарий с именем view и ролью:

```fsharp
connection.ExecuteQuery (prefix + viewExpr.Query.Expression.ToSQLString()) parameters ...
```

Это значит, что один и тот же view под разными ролями – разные строки, то есть разные слоты в кэше подготовленных выражений. Лимит в 50 слотов на соединение при десятках view × десятках ролей приводит к постоянному вытеснению: PostgreSQL заново парсит и планирует запрос.

**Что делать.** Либо вынести идентификацию запроса из SQL-текста в `application_name`/лог, либо поднять `MaxAutoPrepare` до величины, покрывающей реальную кардинальность `(view, role)`, и проверить по `pg_prepared_statements`, что вытеснения нет. Сначала – измерить: в Npgsql есть счётчики, а в PG – `pg_stat_statements`.

## P2. Мелочи на горячем пути

**Логирование без guard.** [SQL/Query.fs:199](../OzmaDB/src/SQL/Query.fs#L199):

```fsharp
logger.LogDebug("Executing query with args {args}: {query}", pars, queryStr)
```

Вызывается всегда, независимо от уровня. Само по себе дёшево (Serilog откладывает форматирование), но боксирует `pars` (F# `Map`) и аллоцирует `obj[]` на каждый запрос. Обернуть в `if logger.IsEnabled(LogLevel.Debug)`.

**`JsonSerializer.CreateDefault()` на каждый ответ.** [HTTP/Utils.fs:234](../OzmaDB/src/HTTP/Utils.fs#L234), [Preload.fs:101](../OzmaDB/src/Operations/Preload.fs#L101). Кэш контрактов при этом сохраняется (`JsonConvert.DefaultSettings` возвращает один и тот же объект настроек – [Program.fs:702](../OzmaDB/src/Program.fs#L702)), так что катастрофы нет, но сам сериализатор пересоздаётся впустую. Держать один экземпляр на процесс.

**Синхронная сериализация ответа.** Там же, комментарий в коде это признаёт: `// Convert that to async when we move to System.Text.Json`. При больших ответах поток блокируется на записи в поток, а после добавления brotli/gzip – ещё и на сжатии. Стоит хотя бы убедиться, что запись идёт в буферизованный поток, а не мелкими кусками в сокет.

**`ExprParameters = Map<int, Value>`** – персистентное дерево для нескольких параметров, с `name.ToString()` на каждом ([SQL/Query.fs:194](../OzmaDB/src/SQL/Query.fs#L194)). Мелочь, но на горячем пути; массив или `Dictionary` уместнее.

## P3. Инфраструктура сборки и версии пакетов

**Где:** [OzmaDB.fsproj](../OzmaDB/OzmaDB.fsproj)

```xml
<TargetFramework>net10.0</TargetFramework>
...
<PackageReference Include="Npgsql" Version="8.0.*" />
<PackageReference Include="Microsoft.EntityFrameworkCore" Version="8.0.25" />
<PackageReference Update="FSharp.Core" Version="8.0.*" />
```

Проект уже собирается под **.NET 10**, но тянет стек пакетов 8.x. Это работает, но означает, что перф-улучшения Npgsql 9/10 (заметно переработанный слой чтения и batching) и EF Core 9/10 не применяются. `FSharp.Core 8.0` на .NET 10 – та же история, там были ускорения в том числе printf-механики.

Отдельно: `SelfContained` + `PublishSingleFile` **без** `PublishReadyToRun`. Весь код джитится при старте, что даёт медленный холодный старт и медленные первые запросы. Для модели «много инстансов, часть перезапускается» это заметно.

**Что делать:**
- Поднять Npgsql и EF Core до 10.x, FSharp.Core до актуальной. Это отдельная задача с проверкой на регрессии, не «в рамках перф-правки».
- Добавить `<PublishReadyToRun>true</PublishReadyToRun>` и измерить время до первого успешного запроса.
- `<TieredPGO>` в .NET 8+ включён по умолчанию, отдельно ставить не нужно. `ServerGC` Web SDK включает сам.

## Чего в коде НЕТ (проверено, беспокоиться не о чем)

Чтобы не тратить время на ложные направления:

- **Нет квадратичной конкатенации списков** – оператор `@` не используется ни разу.
- **Нет блокирующих вызовов** – ни `.Result`, ни `.Wait()`, ни `GetAwaiter().GetResult()` на горячем пути.
- **Все регулярки компилируемые** – `RegexOptions.Compiled` везде.
- **EF Core в режиме NoTracking** глобально ([Connection.fs:101](../OzmaDB/src/Connection.fs#L101)).
- **`%A`-форматирование не используется** ни разу (это обычно главный убийца перфа в F#-логах).
- **`InvariantGlobalization=true`** – уже выставлено.

Код в целом написан аккуратно; проблемы – архитектурные (отсутствие кэшей там, где они напрашиваются) и «инфраструктурные» (рефлексия в сериализации, `sprintf` в рендеринге), а не результат небрежности.
